# 08 · 文本赛道的差异化路径

- 生成时间：2026-10-14T05:10:00+08:00
- 前提：赛道＝文本记忆；组别＝开源方法榜
- 依据：✅ AML 官网 `/competition` 与 `/rules`（2026-10-14T01:23+08:00 抓取）、✅ `02-papers.md`（arXiv API 实测）、✅ `03-projects.md`（GitHub API 实测）

## 0. 结论摘要

> **不要做"更好的通用记忆框架"——那是最拥挤的赛道。**
> 差异化只能来自三处：**① 主流框架系统性缺失的能力项；② 面向"固定 reader"的检索校准；③ 用真实业务把抽象能力项钉死在具体痛点上。**

主张（一句话定位，候选）：

- **A（首选）**：*"面向顺序评分的证据编译"* —— 在 Top-K 上限内做**减法**：去冲突、去重、链条化、自适应证据预算，而不是堆候选。
- **B**：*"时间正确的记忆"* —— 双时间轴（有效时间/记录时间）+ 槽位化状态 + 冲突消解，保证"在问的那个时间点上事实是对的"。
- **C**：*"守边界的记忆"* —— 规则约束记忆 + 敏感信息分级 + 精确的"无证据"信号。

建议：**主攻 A，A 必须叠加 B 作为基线，C 作加分项。**

## 1. 为什么"做个更好的通用记忆框架"没有差异化

✅ GitHub API 实测（`03-projects.md`）：

| 框架 | ⭐ | 定位 |
|---|---|---|
| mem0ai/mem0 | 67,115 | 通用长期记忆层（含抽取+更新+检索） |
| run-llama/llama_index | 52,478 | 通用 RAG 框架 |
| topoteretes/cognee | 32,182 | 图记忆管线 |
| getzep/graphiti | 31,710 | 时间知识图谱 |
| supermemory | 31,204 | 记忆 API |

结论：**"通用记忆框架"已高度同质化**（Mem0/Graphiti 级别的开源底座随手可得），任何人 3 天就能搭出一个"能跑通"的系统。靠它拿奖，等于和 60k★ 的项目比工程完备度，赢面极低。

**真正的差异化不在"能不能记住"，而在"哪些情况下主流方案会答错"。**

## 2. 差异化的可行空间：AML 把评分切成了两半

✅ 官方原文（`/rules`）：

> `你只负责 Add / Search 环节。回答模型、提示词、评分器、数据集组合、Top K 和汇总规则由我们统一固定`
> `参赛方实现记忆写入与检索；平台统一完成回答与评分。`
> `Same answer 同一回答模型 —— 检索结果进入一致的 Answer 合约，隔离生成差异。`

### 关键推论（本文最重要的判断）

```
最终得分 ≈ Add/Search 输出的内容质量（含顺序）
                ↑
        这就是被评分的对象本体
```

由此可得三条硬结论：

1. **你无法通过"更好的生成"得分。** 生成是平台的。
2. **你唯一的杠杆是：交给 Reader 的证据「对不对、全不全、脏不脏、顺序对不对」。** 官方明确 `返回顺序就是证据优先顺序` ✅ —— 顺序直接参与计分。
3. **Top-K = 100 是上限，不是下限。** ✅ 官方原文：`返回的记忆数量不得超过该值`。→ **"少而准"在规则上是被允许的**，这是一个被主流方案忽略的合法策略空间。

> ✅ **用户澄清（2026-10-14，非官方文档口径）**：Reader（Answer）模型**不参与排序与评分**；最终评分对象是 **Add/Search 的输出内容本身，且顺序计入考量**。
> → 本文件的主攻方向**不再依赖"Reader 很弱"这一假设**：我们优化的对象就是被评分的对象本身，这比"迁就读者"更直接。位置效应的机制依据与设计落地见 `10-positional-effects-and-ordering.md`。

## 3. 三组可差异化能力（对齐官方能力项）

官方文本赛道能力模型（✅ 逐字照录，`/competition`）：

| 组 | 能力项 | 官方描述要点 |
|---|---|---|
| 01 RECALL 召回证据 | **A** 显式事实召回 | 事实、属性、来源与实体信息 |
| | **B** 关系与多跳组合 | 跨片段证据与关系链恢复 |
| | **C** 时间与事件序列 | 日期、间隔、顺序与轨迹变化 |
| 02 ADAPT 形成稳定记忆 | **D** 记忆治理 | 更新、冲突消解、删除与遗忘 |
| | **E** 个性化与关怀 | 偏好、背景、健康与心理关怀 |
| 03 ACT 安全执行 | **G** 规则与流程执行 | 领域推理、程序执行与格式约束 |
| | **H** 认识论安全与隐私 | 稳健拒答、最小披露与证据边界 |

### 3.1 「时间正确」包 —— 覆盖 C + D（**必备基线**）

- **主流现状**：大多数系统只存 `created_at`，不区分"事实何时为真"与"我们何时记录"。Zep/Graphiti 做了有效期（✅ `02-papers.md` B1），但开源生态普遍仍是 last-write。
- **做法**：
  1. **双时间轴（bitemporal）**：`valid_from/valid_to`（事实有效区间）+ `recorded_at`（写入时间）。检索时按问题的时间指涉做 scoping。
  2. **槽位化状态**：把"地址/职位/偏好"等高冲突字段建成**单值槽位 + 历史版本链**，而非平铺 chunk。
  3. **冲突消解策略**：来源权威 + 时间新近 + 一致性检查（而非纯 last-write）。
- **⚠️ 重要警示**（✅ 论文 2610.09193）：已有研究指出，某些"冲突消解"增益可能只是 **last-write 记账**带来的假象。→ **上线前必须先跑 last-write 基线**，否则可能白做。

### 3.2 「证据校准」包 —— 覆盖 A + B + H（**主攻方向**）

这是我认为**差异化最大**的一处，因为它针对的是**所有主流方案的共同盲点**：它们都在优化"召回更多"，没人优化"**交给评分环节的那份证据列表本身**（内容 + 顺序）"。

四项具体机制：

1. **约束违约检测**：只要某条候选与 schema/类型/必填约束冲突（例：日期格式、数值区间），**在排序阶段直接降权/剔除**，而不是留给 Reader 去纠错。
2. **链式证据组装（面向 B）**：多跳问题不返回"散落的碎片"，而是返回**证据链**（A→B→C 的连通片段）。多跳的中间环节若散落在多条里最易被忽略（位置效应，见 `10-positional-effects-and-ordering.md`），组装成一条连通证据可保住这一跳。
3. **自适应证据预算（面向 A/H）**：`top_k` 不固定填满 100，而是按**证据置信度断崖**自适应截断（例如只返回到分数陡降前）。这是规则允许的（✅ 上限 100）。
4. **精确的"无证据"信号（面向 H）**：官方要求 `Search 不得直接生成最终答案，也不得把答案伪装为记忆记录` ✅。反过来说，**当确实没有证据时，返回 `{"data": []}` 是最诚实也最正确的动作**——过度返回会让 Reader 编答案，直接违反 `稳健拒答` 的考核意图。

> **差异化要点**：把 Search 从"排序函数"升级为**证据编译器**（compiler）：输入候选，输出"**可直接进入评分的最小充分证据集**"，其中**顺序本身就是被评分的维度**。

### 3.3 「规则与隔离」包 —— 覆盖 G + E + H（**加分项**）

- **规则记忆（G）**：抽取"用户/领域声明的约束"（例：`我们的 SLA 是 P99 < 200ms`、`不要给客户发邮件`），存为**一等实体**，检索时**强制注入**而不参与相似度竞争。主流框架几乎不做——它们把规则当普通文本，于是规则经常输给语义相似的闲聊。
- **敏感分级与最小披露（E/H）**：对健康/心理/身份类记忆打敏感级别，检索时按需最小化与脱敏。
- **隔离验证**：`user_id` 是唯一检索边界 ✅，需要**对抗性测试**（构造跨 user 的语义近似记忆，断言绝不串库）。这是**红线**，一次串库可能取消资格。

## 4. 六个具体痛点场景（场景 × 痛点 × 对应能力项）

| # | 场景 | 痛点（现状会答错的地方） | 能力项 | 差异化做法 |
|---|---|---|---|---|
| S1 | 客服/售后助理：用户 3 个月前说"搬到朝阳区"，2 周前说"先寄到公司" | 冲突记忆并存，返回旧地址 → 答错；纯 last-write 又会丢失"哪个是长期"的判断 | C+D | 槽位化地址 + 双时间轴；冲突按来源与时间消解 |
| S2 | 个人助理/健康关怀：用户提过过敏史、用药、情绪状态 | ① 敏感信息被无关问题带出；② 跨用户张冠李戴；③ 无证据时硬答 | E+H | 敏感分级 + 最小披露 + `{"data":[]}` 校准 |
| S3 | 跨会话项目协作：需求在多轮中逐步定义（"SLA 是 P99<200ms"） | 规则散落在长会话里，后续会话一问就漏；规则输给语义相近的闲聊 | G | 规则抽取为一等实体 + 检索时强制注入 |
| S4 | 长周期指标跟踪：某指标随时间反复变化（价格/评分/状态） | 查询"当时是多少"时返回了最新值；同一实体的多个版本互相冲突 | B+C+D | 时间对齐的事实版本管理（同一实体多版本并存 + 按时间点/区间查询） |
| S5 | Streaming：用户刚说完新信息，立刻问一个需要该信息的问题 | 写入最终一致性延迟 → `写后可见` 不成立；或旧快照污染 | Streaming | 同步可见 + 快照隔离（见 `05-tech-stack.md`） |
| S6 | 32 个数据源的噪声干扰 | 高相似度但语义不同的干扰项挤占 Top-K，把真证据挤出顺序前列 | A+B | 去重/冲突检测 + 来源可信度 + 自适应预算 |

> 说明：S1–S6 是**基于官方能力项与公开基准形态推导的场景映射**，不是官方公布的题型分布。⚠️ 各能力项在 6000+ 实例中的**占比未知**（已列入 `07-open-questions.md`），这直接影响"该往哪个能力项押注"。

## 5. 与现成组件的关系（不重复造轮子）

差异化必须建在成熟底座上，否则 17 天做不完。

| 层 | 用现成的 | 自研（差异化所在） |
|---|---|---|
| 存储 / 向量检索 | pgvector / LanceDB / txtai | — |
| 图与时间图谱 | graphiti 等（如需多跳/时效） | 双时间轴建模与槽位化状态设计 |
| 重排 | Qwen3-Reranker / bge-reranker-v2-m3 | 约束过滤与"证据断崖"截断策略 |
| 抽取 | gpt-4o-mini（FAQ 05 保守分支） | 槽位 / 规则 / 敏感分级的 schema 设计 |
| **证据编译层** | **无现成等价物** | **← 主攻方向，见第 3.2 节** |

**判断**：主流框架都在"存与取"上做文章；"把候选编译成可直接进入评分的最小充分证据集（含顺序优化）"这一层**没有成熟开源实现**，是差异化的真实落点。

## 6. 如何证明差异化真的有效（可测量性设计）

不做这件事，所有"差异化"都只是故事。建议：

1. **建立能力项对照表**：把 A/B/C/D/E/G/H **各造 20–50 条本地测试题**（可用 LoCoMo 2402.17753 / LongMemEval 2410.10813 的公开划分改写），确保每个能力项都有独立可测集。
2. **先跑 3 条基线**（关键，顺序不能反）：
   - `B1 纯向量 top-k`（最弱基线）
   - `B2 last-write`（对抗"冲突消解"虚假增益，见 3.1 警示）
   - `B3 Mem0/Graphiti 类现成框架`（同质化天花板）
3. **每个差异化机制单独 A/B**：只开"链式证据"、只开"自适应预算"、只开"双时间轴"，看各自在**对应能力项**上的增量。
4. **记录负面结果**：无增益的机制直接砍掉（17 天工期不允许堆砌无效复杂度）。
5. **`user_id` 隔离对抗测试**：必须 100% 通过，这是红线。

## 7. 风险与对冲

| 风险 | 对冲 |
|---|---|
| 冷门能力项（D/E/G/H）**题目占比可能很低**，投入产出比不明 | 先保证 A/B/C（大概率是主体）达到基线水平；差异化只加在边际成本低的能力项上 |
| "做减法"若评分实际依赖**完整候选覆盖面** → 少给证据反而丢分 | 自适应预算设为可切换开关；用**位置感知的命中率指标**（首次命中位置、前 k 命中率、MRR）在"少而准"与"全而广"两个方向各测一遍再定 |
| 多机制叠加后写入延迟超 `30 分钟/请求` ✅ | 写入侧机制做成可插拔；必要时把重计算放到"平台允许的同步等待"内并行 |
| 官方能力项编号跳号（缺 F、I，见 `07-open-questions.md` §4）→ 可能存在未公开的考核维度 | 保持架构可扩展（能力项以插件形式注册），不把假设写死 |
| 与 60k★ 框架正面比拼工程量 | 不做通用框架；**只在 Add/Search 的"证据编译"这一层做深**，底层直接用现成组件（txtai / pgvector） |

## 9. 一句话回答用户的问题

> **"文本赛道怎么做出差异化？"**
> 不要比"谁记得多"，要比**"谁在最容易出错的四类情况里不出错"**：
> **① 事实随时间变了（C/D）；② 证据又脏又散、还混着冲突（A/B/D）；③ 该拒绝的时候却硬答（H）；④ 用户定的规则被遗忘（G）。**
> 而这四类恰好是主流开源框架**共同的结构性盲点**——它们都在优化"召回更多"，没人优化"**交给评分环节的那份证据列表（内容 + 顺序）**"。
