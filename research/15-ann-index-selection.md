# 15 · 向量索引选型（ANN）：官方规模下该不该上、上哪一种

- 生成时间：2026-10-25
- 前提（已定）：组别 = **开源方法榜**；赛道 = **多模态记忆（Multimodal）**；服务 = `mem-pro`（纯标准库 + 可选 numpy）
- 关联：`05`（技术栈）、`13`（多模态方向）、`14`（站点复核）
- 结论一句话：**在官方规模下不上 ANN；精确扫描更快、更准、更省运维。** 本文给实测证据、触发阈值和真要上时的落地方式。
- 复现：`tools/ann_bench.py`（本文所有数字均可用一条命令重跑）

---

## 0. 决策表

| 方案 | 11k 条/用户 R@10 | P50 | 构建（每用户） | 增量写入 | 依赖 | 结论 |
|---|---|---|---|---|---|---|
| **精确扫描（现状）** | **1.000** | 3.17 ms | 0 | 追加式索引扩展 50–65 ms | 无（numpy 可选） | ✅ **保留** |
| IVF-Flat nprobe=16 | 0.950 | 0.41 ms | 0.76 s | 需重训质心 | faiss | ❌ 召回 -5%，只省 2.8 ms |
| IVF-PQ nprobe=32 | 0.642 | 0.18 ms | 8.7 s | 同上 | faiss | ❌ QPS 场景才考虑 |
| HNSW efSearch=128 | 0.996 | 0.38 ms | 1.65 s | 图插入需加锁/合并 | faiss/hnswlib | ❌ 每用户 1.65 s 建图不划算 |
| LSH（符号随机投影） | 未达标（同类实现通常 <0.95） | — | 低 | 追加友好 | 无 | ❌ 召回不可控 |

> 表内为**真实 `text-embedding-v4` 向量**（`data/atm_vecs.npy`，11,034 × 1024）与 300 条官方 ATM-Bench 问题的实测，详见 §2.2。

**判据不是「ANN 快多少」，而是「快到的那几毫秒值不值召回损失 + 每用户构建 + 依赖」。** 当前 Search 端到端 P50 约 25 ms，其中精确点积 3 ms；ANN 最多省 12%，却要付出召回 0.4–5% 和每用户秒级构建。

## 1. 官方规模与检索范围（一手原文）

| 事实 | 原文 | 对本选型的含义 |
|---|---|---|
| 多模态赛道 ≈5,000 实例 / 800M tokens | `≈5,000 EVALUATION INSTANCES`、`≈800M TOKENS` | 数据量大，但**分散在多个实例** |
| 文本赛道 6,000+ 实例 / 300M tokens | `6,000+ EVALUATION INSTANCES`、`≈300M TOKENS` | 同上，单实例 ≈5 万 token |
| **检索范围是会话级** | 接入示例 `"user_id": "eval:run_abc123:locomo:conv-0"` | **每个 user_id 的向量数是几十到几百，不是百万** |
| 分段规则 | `20 条消息 或 2,000 个词` 确定性分段 | 单会话按段写入，条数与轮次同阶 |
| 单请求最长 30 分钟 | `单次请求最长 30 分钟` | 延迟不是硬约束，没有必要为此牺牲召回 |

两个公开基准的实际粒度：

- **ATM-Bench**：一个人 4 年的全部记忆才 **11,034 条**（邮件 6,742 + 图像/视频），1,038 道题。
- **Mem-Gallery**：240 段多会话对话 / 3,962 轮 / 1,711 QA → **每段对话 ≈16 轮**。

⇒ 我们能构造的**最大单用户**规模就是 11k 条量级；对话级 user_id 则只有 200 条量级。ANN 的收益区间（>10 万条）在官方数据里不出现。

## 2. 实测

### 2.1 对话规模（真实 v4 向量切片，200 条官方问题）

| n（每条记忆数） | 精确 P50/P95 | 最佳 ANN | 结论 |
|---|---|---|---|
| 200 | **0.02 / 0.04 ms** | IVF nprobe=5：0.03 ms（R=1.0，建 86 ms）；HNSW ef=128：0.05 ms（R=1.0，建 16 ms） | **ANN 比精确还慢** |
| 1,000 | **0.80 / 2.85 ms** | HNSW ef=128：0.14 ms（R=0.998，建 269 ms） | 省 0.66 ms，损失 0.2% 召回 |

### 2.2 单用户上限规模（真实 v4 向量，11,034 条，300 条官方问题）

| 配置 | R@10 | P50 | P95 | 构建 | 索引内存 |
|---|---|---|---|---|---|
| **exact（现状）** | **1.000** | **3.17 ms** | 6.41 ms | 0 | 43 MiB（原始） |
| IVF-Flat nprobe=4 | 0.814 | 0.11 | 0.18 | 0.76 s | 43 MiB |
| IVF-Flat nprobe=16 | 0.950 | 0.41 | 0.89 | 0.76 s | 43 MiB |
| IVF-PQ m=64 nprobe=32 | 0.642 | 0.18 | 0.28 | 8.7 s | **1 MiB** |
| HNSW M=16 efSearch=32 | 0.970 | 0.22 | 0.48 | 1.65 s | ~50 MiB |
| HNSW M=16 efSearch=128 | 0.996 | 0.38 | 0.54 | 1.65 s | ~50 MiB |

读法：想要 R@10 ≥ 0.99，HNSW 要 efSearch=128（0.38 ms），只比精确快 8 倍、绝对值省 2.8 ms；IVF 在同一召回下反而更慢且达不到 0.99。IVF-PQ 省内存 43×，但召回掉到 0.64——**用召回换内存，在本次评分体系里不划算**。

### 2.3 外推：精确扫描什么时候真的变慢（合成聚类数据）

| n | exact P50/P95 | IVF nprobe=16 | IVF nprobe=4 | HNSW ef=128 |
|---|---|---|---|---|
| 11,000 | 2.53 / 8.02 ms | 0.36 ms（1.000） | 0.14 ms（1.000） | 0.30 ms（0.980） |
| 50,000 | 11.33 / 16.29 ms | 0.82 ms（1.000） | 0.26 ms（1.000） | 0.32 ms（0.778） |
| 200,000 | 55.11 / 86.76 ms | 0.67 ms（1.000） | 0.31 ms（0.910） | —（未测） |

精确扫描成本 ≈ `N × dim × 4 B` 内存 + `O(N·dim)` 点积：**每 11k 条 ≈3 ms**。所以在 **5 万条/用户以上**或 **P95 超过搜索总预算的 20%** 时，ANN 才开始有实际意义。

## 3. 为什么现在不引入（四条独立理由）

1. **规模不匹配**：官方 `user_id` 是会话级；对话 200 条时 ANN 比精确慢，11k 条时只省 3 ms。
2. **Add 是追加语义**：我们把索引做成 append-only 扩展（50–65 ms/6.7k 条）。IVF 质心会随数据漂移必须定期重训，HNSW 图插入既要全局锁又要合并，都会破坏「写后立即可搜」的确定性与延迟。
3. **依赖与运维**：faiss/hnswlib 需编译或装 wheel，镜像变大、平台差异变多；当前设计「纯标准库 + 可选 numpy」是部署简单性的主要来源。
4. **召回不可见**：ANN 损失只体现在评测分数上，本地没有金标就无法调 nprobe/efSearch。宁可零风险。

补充：`RANK_INDEX_MAX_MB=64` 意味着单用户 1024 维向量缓存上限 ≈16k 条。**真正的悬崖是这条预算线，不是 ANN**：超过它我们退回逐文档 unpack（更慢但结果不变），而 ANN 会把「变慢」换成「变不准」，更难发现。

## 4. 触发条件与真要上时的落地方式

### 4.1 触发阈值（任一满足才重新评估）

| 指标 | 阈值 | 检查方法 |
|---|---|---|
| 单 user_id 记忆数 | ≥ 50,000 | `/stats` 按用户统计，或 `store.count(user_id)` |
| 精确点积 P95 | ≥ 20 ms 或 ≥ 搜索总耗时的 20% | Search 日志 `search_rank_ms` |
| 单进程 CPU 饱和且加进程无效 | 吞吐瓶颈确认为点积 | `tools/search_load.py` + 分阶段日志 |

### 4.2 若触发，按此顺序落地

1. **先扩进程**（多 worker + 反代）：成本最低、召回不变；精确扫描是 CPU 并行友好的。
2. **再换 IVF-Flat（faiss）**：`nlist≈√N`，`nprobe` 调到 R@10 ≥ 0.99（本文数据约需 16+）；保留精确路径作为回退开关（`ANN=off`），并用 `tools/ann_bench.py --vectors ... --questions ...` 每次改动后复测。
3. **不建议 PQ**：除非内存成为硬约束（当前 11k 条仅 43 MiB，不构成约束）。
4. **不建议 HNSW**：除非单用户 ≥ 20 万条且写入稀少；建图 1.65 s/11k 与追加写入冲突。

任何 ANN 上线都必须带一条**召回回归**：在标注 query 上比较 ANN 与精确的 R@10/top-1，差值 > 0.01 即回滚。

## 5. 复现

```bash
# 需要 numpy；IVF/HNSW/PQ 行需要 faiss-cpu
pip install numpy faiss-cpu

# 真实 text-embedding-v4 文档向量 + 官方问题（query 走当前 EMBED_MODE）
python3 tools/ann_bench.py --vectors data/atm_vecs.npy \
    --questions data/atm-bench/atm-bench.json --queries 300

# 对话规模切片
python3 tools/ann_bench.py --vectors data/atm_vecs.npy --questions data/atm-bench/atm-bench.json --limit 200

# 合成外推（无 faiss 也能跑 exact 行）
python3 tools/ann_bench.py --n 11000,50000,200000 --dim 1024 --queries 50
```

输出：`R@k`、P50/P95、每用户构建耗时、索引内存。ground truth 由精确扫描给出，因此 Recall 是**相对当前生产实现**的真实损失。

## 6. 已知局限

1. ATM-Bench 是**单人**语料；官方评测是否给出更大的单 user 记忆量，公开材料未说明（见 `07`）。若出现 10 万条级单用户，按 §4.2 走。
2. 合成聚类数据只用于**外推**精确扫描的延迟曲线，不代表官方分布。
3. faiss 版本为 1.15.1（本地 `faiss-cpu`），不同版本的 HNSW 默认参数可能不同；比较时始终以「同 R@10 下的延迟」为准。
