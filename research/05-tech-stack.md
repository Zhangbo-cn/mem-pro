## 一、必须满足的接口契约（硬约束，先背下来）

| # | 约束 | 官方原文 |
|---|---|---|
| 1 | 同步写入 | `记忆写入完成后，Add 接口返回 HTTP 200`；`每个记忆分块都必须在返回 HTTP 200 前完成持久化，并且能够立即检索。` |
| 2 | Top K | `正式外部评测固定为 100`；`返回数量不得超过 top_k ，超量会判为契约错误` |
| 3 | user_id 隔离 | `Add 和 Search 必须使用完全相同的 user_id`；`禁止跨 user_id 返回记忆` |
| 4 | session_id 不作筛选 | `session_id ... 不作为 Search 的筛选条件` |
| 5 | 鉴权 | `支持 Token 、 Bearer 和 X-Api-Key ； none 仅用于公开 smoke` |
| 6 | 不发送字段 | `不发送 metadata 、 app_id 、 agent_id 或 async_mode` |
| 7 | 响应形态 | 顶层 `data` 数组；`不要增加 items 包装层`；无结果 `{"data": []}` |
| 8 | 返回顺序 | `返回顺序就是证据优先顺序`；`我们保留接口返回的顺序` |
| 9 | 地址 | HTTPS；`不得包含用户名、密码等凭据，也不得指向私有、回环或链路本地地址` |
| 10 | 超时 | `单次请求最长 30 分钟` |
| 11 | 健康检查 | `Health 接口通过无需鉴权的 GET 请求调用，返回任意 2xx 状态码即表示服务正常` |

**禁止**（官方）✅：Search 不得直接生成最终答案、不得把答案伪装成记忆、不得跨 user_id 共享记忆、不得硬编码/提示词注入/人工实时答题。

## 二、MVP 架构（目标：**通过 Smoke**，工期最短）

```
AML 平台
  │  POST /add     (request_id, messages[], user_id, session_id)
  │  POST /search  (query, user_id, top_k=100, options?)
  ▼
FastAPI (uvicorn)  ── 鉴权中间件 (Token | Bearer | X-Api-Key)
  │
  ├─ Add 服务：分段(20 msgs / 2000 words) → 逐条持久化 → 返回 200
  │     └─ 向量化: text-embedding-v4
  │
  └─ Search 服务：向量检索 top_n(≈200) → Reranker 重排 → 截断到 top_k → 组装 {"data":[...]}
        └─ 重排: Qwen3-Reranker-4B 或 bge-reranker-v2-m3
  ▼
存储: PostgreSQL + pgvector（单库，user_id 强制过滤）
     或 SQLite + sqlite-vec / LanceDB（更轻，单机即可）
```

### 组件清单（MVP）

| 层 | 组件 | 理由 |
|---|---|---|
| Web | `FastAPI` + `uvicorn` | 异步模型贴合「同步写入 + 立即检索」；依赖轻、单机可跑；接口契约清晰 |
| 鉴权 | 自写依赖注入，支持 `Authorization: Bearer/Token` 与 `X-Api-Key` | 官方只要求三种之一；`none` 仅限 smoke |
| 向量化 | `text-embedding-v4`（DashScope） | FAQ 05 保守分支；维度取 1024（默认） |
| 存储 | `PostgreSQL + pgvector` 或 `LanceDB` | 单库解决持久化 + 向量检索；`user_id` 做**强制 WHERE 过滤** |
| 重排 | `Qwen3-Reranker-4B` / `bge-reranker-v2-m3` | 官方明确 Reranker 不限 ✅，是唯一能自由选强模型的环节 |
| 分段 | `20 条消息 或 2,000 词`（以先到者为准） | **官方确定性规则** ✅，必须照做，否则与评测切分不一致 |
| 观测 | 结构化日志（request_id / 耗时 / 错误） | 官方保留审计记录；`格式错误立即终止`，需可快速定位 |

### 「写后可见」的实现要点（最容易踩坑）

✅ 官方：`服务内部可以采用异步处理，但 Add 接口必须等待处理完成后再返回。`

- ❌ 错误做法：把写入丢进队列立即返回 200 → 违反契约，`未绑定时返回 202 属于契约错误`。
- ✅ 正确做法：**同步等待**向量化 + 持久化落盘成功后再返 200；可用内部批处理优化吞吐，但必须在同一请求内 await 完成。
- ⚠️ HTTP 202 仅在**已审核绑定 `{task_id}` 的 Add 状态查询地址**时才支持，MVP **不要用 202**。

### 性能风险

- ≈300M tokens 的写入量 + 同步语义 = **写入吞吐是最大瓶颈**。
- 对策：批量向量化请求（`text-embedding-v4` 单次最多 10 行 ✅，需并发多请求）；提前预热连接池；对 embedding 做本地缓存（同文本去重）。

## 三、冲榜架构（进阶：针对 AML 的能力项加分）

MVP 只保证"能跑通"。要提分需覆盖官方能力项：`A 显式事实召回`、`B 关系与多跳组合`、`C 时间与事件序列`、`D 记忆治理`、`E 个性化与关怀`、`G 规则与流程执行`、`H 认识论安全与隐私`。

```
                     ┌──────────────── 写入侧 (Add) ────────────────┐
messages[] ──► 分段(20/2000) ──► 抽取器(gpt-4o-mini)
                     ├─► 事实/属性三元组  ──► 关系与时间图谱 (Graphiti)
                     ├─► 时间事件(带有效期) ──► 时间索引
                     ├─► 用户画像/偏好     ──► 画像库 (E 个性化)
                     └─► 规则/流程约束     ──► 规则库 (G 规则执行)
                                    │
                                统一向量化 (text-embedding-v4)
                                    ▼
                      多路索引: 向量库 + 图库 + 画像库 + 规则库
                     └──────────────── 读取侧 (Search) ───────────────┘
query ──► 查询改写/扩展(HyDE、多查询) ──► 多路召回(并行)
              ├─ 向量召回 top_n
              ├─ 图多跳召回 (Personalized PageRank / HippoRAG 思路)
              ├─ 时间过滤召回 (按 query 时间线索)
              └─ 画像/规则召回
                    ▼
         融合去重 + 冲突消解(更新/失效: 时间戳优先 + last-write 对照)
                    ▼
         重排 (Qwen3-Reranker-4B) + 证据质量自检(只返回证据, 不生成答案)
                    ▼
         截断到 top_k=100, 按相关性降序组装 {"data":[...]}
```

### 进阶组件选型

| 能力项 | 建议组件 | 参考 |
|---|---|---|
| 写入抽取/摘要 | `gpt-4o-mini`（FAQ 05 保守分支） | `04-models.md` |
| 关系/多跳 + 时间 | `graphiti`（31.7k★，时间知识图谱）或 `cognee`（32.2k★，图管线） | `03-projects.md` |
| 图多跳召回 | 个性化 PageRank 思路（HippoRAG） | `02-papers.md` B4 |
| 分层摘要 | RAPTOR 方法（⚠️ 官方 repo 停滞，**借方法不借依赖**） | `02-papers.md` C1 |
| 记忆治理（遗忘/冲突） | 引用 MemoryBank 遗忘曲线 + 知识冲突综述策略 | `02-papers.md` C2 / D1 |
| 冲突消解基线对照 | **先做 last-write 基线**（方法论警示见 D3） | `02-papers.md` D3 |
| 关系/图存储 | Neo4j（成熟）或 Kuzu（嵌入式，轻）；MVP 可先用 pgvector 的关系表模拟 | — |
| 向量库 | pgvector（MVP）→ Milvus/Qdrant（规模上去后） | — |
| 服务化 | FastAPI + uvicorn，配 `/health` 无鉴权 GET ✅ | — |

### 关于"多路融合"的取舍建议

- **不要一次上全**。AML 的 Full 只有 **2 次机会、间隔 30 天** ✅，每次都是稀缺资源。
- 建议节奏：`MVP 单路向量 → + 重排 → + 时间过滤 → + 图多跳 → + 治理`，每加一层都在**本地 LoCoMo/LongMemEval 代理评测**上看增益，无增益就回滚。
- 强提醒（来自论文 D3）：很多"冲突消解/治理"的增益可能只是 **last-write 记账**带来的。**先跑 last-write 基线**，再决定是否投入复杂治理模块。

## 四、本地自测策略（替代无法下载的金标）

AML ✅ `不提供金标答案、评分依据或完整数据集下载`。因此必须自建代理评测：

| 手段 | 说明 |
|---|---|
| 公开基准代理 | LoCoMo（2402.17753）、LongMemEval（2410.10813）——形态与文本赛道最接近（见 `02-papers.md` E1/E2） |
| 合成数据回放 | **自造** Add/Search 往返数据（按官方分段规则生成多轮会话）验证契约与延迟；不依赖任何既有业务数据 |
| 契约测试 | 按官方"格式错误立即终止"清单写断言：`success=true`、三 ID 回传一致、`data` 数组、每条含 `id`/`content`、条数 ≤ `top_k` |
| 隔离测试 | 构造两个 `user_id`，断言**绝不串库**（官方红线） |
| 分段一致性 | 用官方规则（20 条消息 / 2000 词）切分，避免与平台切分错位 |
| 延迟压测 | 模拟 Smoke 的同步写入-立即检索链路，测 P95 |

⚠️ 本地自测**不能**替代官方评测：`正式任务使用统一的数据集套件和 Top K` ✅，题型与指标未必一致。

## 五、开发前提与环境约束（本机实测）

| 项 | 状态 | 影响 |
|---|---|---|
| 可复用的既有记忆系统代码 | **无** —— 需从零建 Add/Search 服务 | 选型必须优先复用成熟**库**，自研只放在差异化的检索编排层 |
| Python 3 / Node | 可用 | 后端可用 FastAPI + pgvector/LanceDB |
| `curl` | 可用 | 用于官方接口联调与自测脚本 |
| 重型依赖 | 任务纪律禁止安装 | 排除需要 GPU、大规模集群的方案；优先单机可跑 |
| 网络（实测） | `github.com` 网页、`huggingface.co` 直连超时；`api.github.com`、`raw.githubusercontent.com`、`arxiv.org` 可达 | 装包与模型下载可能受限，需预留时间（见 `urlcheck.txt`） |

**因此建议**：底层直接用现成组件（检索库 + 向量存储），只自研「证据编译」层（见 `08-differentiation.md`），把 17 天工期集中在差异化上，而不是重造基础设施。

## 六、成本量级（MVP → 一次 Full）

| 项 | 量级 | 备注 |
|---|---|---|
| Embedding | 文本赛道 ≈300M tokens → **≈150 元/次全量**（`0.0005 元/千 Token`） | `04-models.md` 第七节 |
| 内部 LLM（gpt-4o-mini） | 同量处理 ≈ **320 元/次** | 粗估，汇率 7.1 |
| 自测与迭代 | 通常是正式量的 **2–5 倍** | 无金标，需反复代理评测 |
| 存储/带宽/算力 | 官方明确**由参赛方自付** ✅ | 图形/图库会显著抬高 |
| **合计（文本，含迭代）** | 粗估 **千元～数千元人民币级** | ❓ 未做精确测算，需按实际架构复核 |

> 代码赛道（≈1.8B tokens）成本约为文本的 **6 倍**，且本地无法复现代码端到端评测，是成本最不可控的选项。

## 七、落地清单（MVP，按顺序）

1. `POST /add`：鉴权 → 校验必填 → 分段 → 同步向量化 → 落库 → 返回 `{success:true, request_id, user_id, session_id}`
2. `POST /search`：鉴权 → 校验 → 向量召回 top_n → 重排 → 截断 `top_k` → 返回 `{"data":[{id,content,score,created_at}]}`
3. `GET /health`：无鉴权，返回 200
4. 契约测试（含 user_id 隔离、条数上限、非法条目）
5. 本地代理评测（LoCoMo/LongMemEval 子集）
6. 提交 Evaluation Access Request → 绑定版本/接口/鉴权 → Smoke
7. Smoke 通过 → Full（**记住：只有 2 次，第 2 次须 30 天后**）
