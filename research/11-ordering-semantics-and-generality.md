# 11 · 输出顺序的语义定义，与"通用性 × 针对性"的取舍

- 生成时间：2026-10-14T06:20:00+08:00
- 决策记录：**用户已选赛道 = 多模态记忆**（2026-10-14），组别 = 开源方法榜
- 关联：`01`（赛道对比）、`04`（模型）、`06`（材料清单）、`08`（差异化）、`09`（失忆机制）、`10`（位置效应）
- 前提说明：**"Reader 不参与排序与评分，评分对象是 Add/Search 输出（含顺序）"为用户澄清**（非官方文档口径），本文全部推理建立在此之上

---

## 0. 摘要

1. **顺序必须定义，而且多模态下是"两层顺序"** —— `data[]` 的条目顺序（L1）与条目内 `content[]` 的有序内容数组（L2）。官方只说了 `返回顺序就是证据优先顺序` ✅，**未说明覆盖哪一层**。
2. **建议把"顺序"从"相似度降序"重新定义为「证据优先序（evidence precedence）」** —— 表达的是"平台在形成结论时应优先采信谁"，而不是"谁跟我最像"。这两者在失效/冲突/越界场景下结论相反。
3. **通用性 × 针对性的取舍有解** —— 关键不是调权重，而是**把通用性放在"语言层"、把针对性放在"声明层"**：定义一套**声明式排序契约**（属性 schema + 过滤/排序两阶段 + 确定性 tie-break + 约束原语），场景只写声明不改代码。
4. **这件事的价值确实很大**，因为"输出顺序 = 评分对象"使排序契约从**实现细节**升格为**一等产品资产**——而可移植的排序语义具有标准级价值（类比 `ORDER BY` / HTTP 缓存语义）。

## 2. 第 1 问：「解析输出顺序」是否需要定义？

**需要。三个理由，且第三个只在多模态下出现。**

### 理由 A：歧义成本是"沉默的"

"顺序"至少有 6 种合理读法：

| 读法 | 含义 |
|---|---|
| 相关性降序 | 最常见默认（也是大多数开源框架的行为） |
| 置信度降序 | 系统对该条为真的把握 |
| 权威性降序 | 来源可信度 |
| 时效降序 | 越新越前 |
| 模态优先 | 原图优于文本描述 |
| **证据优先序** | "平台应先采信谁"（本文推荐） |

**危险在于**：评审侧按某一种读法解析，而你的实现按另一种排序，会产生**系统性错配且不报错**——你拿到低分，却从日志里看不出原因。这是最贵的一类错误。

### 理由 B：不定义就无法确定性复现

公榜准入要求 ✅：`统一回答模型、评测规范、pipeline code hash、dataset bundle hash 和题量记录必须完整`、`结果不得重复提交`。

若顺序不确定（浮点并列、字典序不稳定、多路召回并行合并顺序随机、哈希遍历顺序），**同一输入可产出不同顺序** → 结果不可复现 → 复核风险。**顺序的确定性是公榜准入的隐含前提。**

### 理由 C（多模态专有）：天然存在**两层**顺序

官方 ✅：`多模态写入 按有序内容数组接收文本和 Base64 图片` —— 说明**内容数组是有序的**。于是返回侧必然有两层：

```
data 数组（L1：条目优先序）
├── item[0]
│   └── content 数组（L2：条目内采信序）  e.g. [ image_url(原图), text(OCR), text(caption) ]
├── item[1]
│   └── content 数组
└── ...
```

**✅ 已澄清（用户，2026-10-14）：「顺序就是 Search 之后的输出顺序」→ 即 L1（`data[]`）的顺序是被评判的顺序。**
> 推论：**L2（条目内 `content[]`）仍需正确解析**（解析错误属契约错误），但**不参与顺序评分**。这一澄清**显著简化了设计**——优化重心完全落在 L1 的跨模态统一排序上。

## 3. 第 2 问：顺序应该怎么定义？

### 3.1 推荐定义：从"相似度"改为「证据优先序」

> **定义（提案）**
> `data[]` 的顺序表示：**平台在形成结论时应优先采信的顺序**。
> `item.content[]` 的顺序表示：**该条证据内部的采信顺序**（主证据 → 辅助证据）。

**为什么必须是这样**：在**失效 / 冲突 / 越界 / 无证据**四类情况下，"相似度降序"与"应优先采信"会给出**相反**的结论：

- 旧地址在语义上可能比新地址**更接近** query（因为 query 提到的是旧情境）→ 相似度排序会把失效证据放前面。
- 一条高相似度的记忆可能**来源不可靠**或**已过期** → 相似度排序会污染前 k。
- 跨主体高相似记忆（同模板不同人）→ 相似度排序会把**越界证据**排进来，直接踩红线。

**因此"顺序"必须承载"采信优先级"，而不只是"相似度"。** 这是本定义的核心价值，也是与主流开源框架（绝大多数就是向量相似度降序）的**结构性差异点**。

### 3.2 通用属性 Schema（7 个，通用层固定）

| 属性 | 含义 | 与官方能力项的对应 |
|---|---|---|
| `relevance` | 与 query 的语义相关度 | A/B |
| `validity` | 在 query 的时间指涉上是否有效 | **C** |
| `authority` | 来源权威性 / 可信度 | **D** |
| `recency` | 事实/记录的时效新旧 | C/D |
| `modality_trust` | **跨模态可信度**（原图 > OCR > caption > 模型生成描述） | 多模态专有 |
| `specificity` | 直接回答 vs 仅间接相关 | A/B/G |
| `provenance` | 可否追溯到原始来源 | **H**（证据边界） |

> 设计原则：**Schema 通用（7 个属性覆盖所有场景），取值与优先级场景化。** 通用性落在"用什么维度描述证据"，针对性落在"这些维度怎么排"。

### 3.3 两阶段：先过滤，再排序（关键结构）

```
阶段 1  FILTER（硬约束，不满足则剔除，不进入排序）
   ├─ 隔离：user_id 边界（红线，绝不可越过）
   ├─ 有效性：在 query 时间指涉内有效（排除失效版本）
   ├─ 合规：不得返回答案/选项字母/外部金标；高敏记忆按授权门槛
   └─ 去重：同一事实的多种表示（原图 / OCR / caption）合并
                ↓
阶段 2  ORDER（软偏好，场景可声明）
   └─ 默认键（lexicographic）：
      specificity → relevance → authority → modality_trust → recency
      确定性 tie-break：created_at 降序 → id 字典序
                ↓
阶段 3  EMIT
   └─ 截断到自适应预算；无证据则显式 {"data": []}
```

**为什么"先过滤后排序"优于"加权和"**：

- 加权和**无法表达"绝不"**。无论权重多大，失效证据仍可能以极小概率进入前 k；而"绝不串库""绝不返回金标"是**红线**，必须是硬约束。
- 加权和对权重的解释性差，难以向评审说明"为什么这样排序"。
- 过滤/排序分离后，**可复现性更容易保证**（过滤是布尔判定，排序有确定性 tie-break）。

### 3.4 顺序层的约束原语（场景可声明，机制通用）

| 原语 | 作用 | 默认 |
|---|---|---|
| `no_conflict_prefix(k)` | 同一事实的冲突版本不得同时进入前 k | 开启 |
| `sensitive_gate(level, k)` | 敏感等级超过阈值者不得进入前 k | 开启 |
| `modality_precedence(原图 > OCR > caption)` | 跨模态采信序 | 开启（可反转） |
| `empty_if_no_evidence` | 无证据必须返回空数组，禁止用低分噪声填充 | 开启 |
| `min_precision(θ)` | 前 k 的最低证据精度，低于阈值则主动收缩 k | 可调 |

### 3.5 确定性（复现性）要求

- tie-break 必须**全序**：`score` 相等 → `created_at` → `id`（字典序）→ 若仍并列，用内容的稳定哈希。
- **声明**排序实现版本（写入 `pipeline code hash` 体系）。
- 禁止非确定性来源进入排序：并行召回结果的合并必须**按稳定键**而非完成顺序。

> 这一条看似琐碎，但它直接决定公榜准入时的可复核性（`06` §七）。

## 4. 第 3 问：通用性 × 针对性，怎么调和？

### 4.1 冲突的根源

通用性要求"一套机制覆盖多场景"；针对性要求"每个场景最优"。冲突的真正来源是：**最优排序键依赖场景的代价矩阵**（`09` §5.1）——而代价矩阵**无法枚举**（场景无限）。

例如同一条"证据预算该收紧还是放宽"，在高并发客服（噪声代价高）与知识型分析（漏召回代价极高）中**结论相反**。

### 4.2 五条路径评估

| # | 路径 | 通用性 | 针对性 | 可解释/可审计 | 可复现 | 结论 |
|---|---|---|---|---|---|---|
| 1 | 枚举场景包（N 场景 N 套配置） | 低 | 高 | 中 | 中 | ❌ 维护爆炸，新场景无解 |
| 2 | 加权和 + 场景权重 | 中 | 中 | **低** | 中 | ❌ 权重不可解释、无法表达"绝不" |
| **3** | **声明式排序契约** | **高** | **高** | **高** | **高** | ✅ **推荐主干** |
| 4 | 学习排序（LTR） | 高 | 高 | **低** | 低 | ⚠️ 无标注数据（**AML 无金标**）→ 只能作可选插件 |
| 5 | 约束满足 / 多目标优化 | 高 | 高 | 高 | **依赖求解器确定性** | ✅ **作为路径 3 的硬约束层实现** |

### 4.3 推荐：**通用性放在"语言层"，针对性放在"声明层"**

> **机制通用 + 策略声明**：属性 Schema、两阶段结构、确定性规则、约束原语 —— 全部通用且固定。
> 场景只写一份**声明**（哪些约束开启、键的次序、阈值、模态可信度先验），**不改代码**。

**为什么这解决了取舍**：

- 通用性体现在**表达能力**上：一套语言能表达所有场景的策略 → 不需要为场景重写引擎。
- 针对性体现在**声明内容**上：每个场景写自己的声明 → 每个场景都能达到它自己的最优。
- 新增场景的成本从"改架构"降为"写一份声明" → **这是可度量的**（见 4.4）。

**类比**：SQL 的 `ORDER BY` 本身是通用的（一套语法），但具体排什么、升序降序是完全针对性的。这正是"通用机制承载针对性策略"的成熟范例。

### 4.4 通用性可以被度量（关键洞察）

通用性不像准确率那样直接可测，但可以定义**接入成本指标**：

| 指标 | 含义 |
|---|---|
| 新增场景所需声明行数 | 越少越通用 |
| 新增场景是否需要修改核心代码 | 应为 0 |
| 新增场景是否需要重训/重算 | 应为 0 |
| 跨场景策略冲突数 | 声明间应无冲突（可静态检查） |

**这四个指标让"通用性"变成了可优化、可汇报的量**，而不只是口号。

## 5. 为什么这个取舍难，以及做好了的价值

### 5.1 难在三处

1. **抽象一旦选错，后患不可逆**：属性 Schema 与约束原语的选型是**一次性投资**。选少了，场景层会退化成 if-else 屎山；选多了，机制臃肿且难以理解。
2. **没有金标可验证**：AML ✅ `不提供金标答案、评分依据或完整数据集下载`。即"声明式契约是否真的更优"**无法端到端验证**，只能用本地代理基准 + 位置感知指标间接验证。
3. **顺序的语义在官方口径里未定义**（第 2 节理由 C），你是在一个**部分未定义的空间**里做设计，必须对不确定性做显式对冲（见 §8）。

### 5.2 做好的价值（正面回答用户的判断）

用户说"如果做好价值也很大"——**这个判断成立，而且理由比直觉更硬**：

1. **它是一等产品资产，不再是实现细节。** 既然"输出顺序 = 评分对象"，那么排序契约就是**被直接评分的东西**，而不是内部管道。定位变了，价值自然变了。
2. **可移植的语义具有标准级价值。** 一个**小而精确、可组合**的约定一旦被采纳会产生网络效应——`ORDER BY`、HTTP 缓存语义、OpenAPI 都是这一类。**"证据优先序"目前没有公认语义，谁先形式化谁定义标准。**
3. **它是"通用性 × 针对性"两难的正解，而这正是别人卡住的地方。** 主流框架（`03-projects.md`，Mem0 67k★ 等）都在做"更好的召回"；**几乎没人把"排序语义"当成可声明的契约**。这是一个低竞争、高杠杆的位置。
4. **它直接降低赛事的两类风险**：可解释性（能向评审说明排序理由）与可复现性（公榜准入的隐含前提）。
5. **在多模态下额外获得一个未形式化的资产**：**跨模态可信度先验**（原图 > OCR > caption > 生成描述）。这个先验在工程实践中普遍存在（专家都知道），但**极少被显式形式化**。形式化它，就是可复用的差异化资产。

## 7. 落地：最小可行排序契约（MVP 版）

| 组件 | 内容 | 工作量 |
|---|---|---|
| 属性 Schema | 7 个属性（§3.2），写入侧负责产出，检索侧负责消费 | 小 |
| 过滤阶段 | 4 条硬约束（隔离 / 有效性 / 合规 / 去重） | 中 |
| 排序阶段 | 默认 lexicographic 键 + 确定性 tie-break | 小 |
| 约束原语 | 5 个原语（§3.4）以配置开关形式实现 | 中 |
| 声明文件格式 | 一份策略声明（约束开关 + 键次序 + 阈值 + 模态先验） | 小 |
| 确定性保障 | 全序 tie-break + 版本声明 | 小 |
| **本地验证** | 位置感知指标（首次命中位置、前 k 命中率、MRR、nDCG）+ `user_id` 隔离对抗测试 | 中 |

> 建议节奏：**先做 L1 单层 + 默认排序键**（能过 Smoke），再引入 L2 与场景声明（差异化）。理由：本届**实际只有 1 次 Full**（`07` §5），可交付性优先。

## 9. 三问三答

> **①「解析输出顺序」需要定义吗？**
> **需要。** 不定义会导致**沉默的系统性错配**（评审按 A 读法、你按 B 排序，扣分但不报错）；无法**确定性复现**（公榜准入的隐含前提）。
> 范围已澄清：**顺序 = Search 的输出顺序（`data[]`，即 L1）**；条目内内容数组（L2）不参与顺序评分，但仍须按规范正确解析。

> **②应该怎么定义？**
> 把顺序从"**相似度降序**"重新定义为"**证据优先序**"——表达"平台应先采信谁"。
> 结构上采用 **先过滤（硬约束）、后排序（软偏好）** 两阶段：过滤保证红线（隔离/有效性/合规/去重），排序使用 7 属性 Schema 的默认 lexicographic 键 + 全序 tie-break，再叠加 5 个场景可声明的约束原语。

> **③通用性 × 针对性怎么调和？**
> **不要把通用性放在"权重"上，要放在"语言"上。**
> 通用层固定：属性 Schema、两阶段结构、确定性规则、约束原语。
> 场景层只写**声明**：约束开关、键次序、阈值、模态可信度先验。
> 于是通用性 = 表达能力（一套语言覆盖所有场景），针对性 = 声明内容（每场景各自最优），**新增场景成本从"改架构"降为"写声明"**，而且这个成本**可度量**（§4.4）。
> 这个取舍确实难（抽象选错不可逆、无金标可验证、官方语义部分未定义），但**做好了的价值是一等资产级的**：可移植的排序语义具有标准级网络效应，而主流框架把排序当实现细节、几乎无人形式化——这是一个低竞争、高杠杆的位置。
