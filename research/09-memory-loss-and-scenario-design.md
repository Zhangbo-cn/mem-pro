# 09 · 记忆的本源：失忆机制分类与场景化设计

- 生成时间：2026-10-14T05:40:00+08:00
- 性质：概念/设计 memo。第 2 节的机制分类中，**只有一项在本项目做过核验**（Lost in the Middle），其余标注为"一般性认知，未在本项目核验"，需时再补证。
- 关联：`05-tech-stack.md`（架构）、`08-differentiation.md`（差异化落点）

---

## 0. 摘要（三句话）

1. **截断只是"上下文组装"阶段的一种表层机制，而且通常是工程策略而非模型机制。** 真正的失忆是一条**五段流水线的复合损耗**，截断往往不是主要矛盾。
2. **窗口变大改变的是问题的形状，不是问题本身**：约束从"容量不足"迁移为"注意力分配与精确定位"——也就是说，**越大的窗口，问题越像检索问题**。
3. **场景化的正确落点在"策略层"，不在"机制层"。** 流水线同构，但"什么算重要、什么算过期、什么算冲突、错了的代价多大"完全依赖场景。→ 产品形态应是**通用引擎 + 场景包（scenario pack）**。

---

## 1. 回到本源：为什么会有"记忆"这个问题

严格说，LLM 没有"记忆丢失"——它**没有记忆**，只有**每次前向计算时被注意力机制加权的一段 token**。

因此记忆问题的本源不是"窗口不够大"，而是：

> **注意力是有限且非均匀的资源。**

窗口大小只是把这个连续的资源配置问题**截断成一个离散的悬崖**（能放进去 / 放不进去）。把窗口从 8K 提到 1M，悬崖后退了，但"资源有限且非均匀"这件事没有消失——只是表现形式从"放不下"变成了"放得下但用不好"。

**证据（本项目已核验 ✅）**：`Lost in the Middle`（arXiv 2307.03172，`02-papers.md` E4）实证发现模型对长上下文**中间位置**的信息利用率显著下降（U 型）。→ 这些 token **在窗口内、没有被截断**，但对任务而言**已经丢了**。

**这就是"截断≠失忆"的直接证据。**

## 2. LLM / 记忆系统的信息损失机制（分层）

### 2.1 模型内机制（**不是截断**）

| 机制 | 说明 | 置信度 |
|---|---|---|
| 注意力稀释 / U 型利用 | 上下文中间的信息被加权不足；token 在但用不到 | ✅ 本项目已核验（2307.03172） |
| 位置外推退化 | RoPE 等位置编码超出训练长度后退化，名义上下文 > 有效上下文 | ⚠️ 一般性认知，未在本项目核验 |
| 注意力结构性偏好 | "注意力汇聚"现象：首尾 token 获得超额权重 | ⚠️ 一般性认知，未在本项目核验 |
| 能力上限 | 证据在上下文里，模型也"看见"了，但推理不出来 | ⚠️ 常识性判断 |

### 2.2 服务/工程层机制

| 机制 | 说明 |
|---|---|
| **硬截断 / 滑窗** | 最常见，最直观——超长就丢头或丢中间。**这是策略选择，不是模型属性** |
| 有损摘要压缩 | 为了塞进窗口而摘要，细节在摘要时就被丢弃 |
| KV cache 压缩 / 驱逐 | 推理框架为控内存而驱逐历史 KV 块——**丢失发生在框架层，模型完全不知情** ⚠️ 未在本项目核验 |
| 检索失败 | 证据**根本没进上下文**（最常见的真实"失忆"） |

### 2.3 记忆系统特有机制（**最关键，也最常被忽略**）

这才是"做记忆"要解决的问题域。它**发生在上下文窗口之前**：

| 阶段 | 典型失败模式 |
|---|---|
| **写入侧** | 该记的没记；LLM 抽取时丢掉关键限定条件；摘要抹平细节 |
| **存储侧** | 被覆盖；新旧冲突共存；过期未失效；跨主体串库 |
| **检索侧** | 召回不到（embedding 语义盲区）；召回了但排序错 |
| **组装侧** | 顺序不对；重复冗余；噪声挤占预算；超预算被裁 |
| **阅读侧** | 模型能力上限（**不可控**；且按用户澄清，Reader 不参与排序与评分 → 不在本项目的优化范围内） |

**关键洞察**：在真实系统里，"记忆不好"的投诉，**根因多数落在 2.3 的前四行**，而不是 2.2 的截断，也不是 2.1 的注意力。

## 3. 失忆流水线（一张表看清谁该负责）

| # | 阶段 | 失败模式 | 是否"截断" | 谁控制 | 可测指标 |
|---|---|---|---|---|---|
| 1 | 写入 | 未抽取 / 细节丢失 | 否 | **你** | 写入召回率（原文事实是否入库） |
| 2 | 存储 | 覆盖 / 冲突 / 过期 / 串库 | 否 | **你** | 冲突率、时效正确率、隔离通过率 |
| 3 | 检索 | 未召回 / 排序错 | 否 | **你** | Recall@k、MRR/nDCG |
| 4 | 组装 | 顺序错 / 冗余 / 噪声 / 超预算 | **部分是**（超预算即截断） | **你** | 证据精度、冗余率、预算利用率 |
| 5 | 阅读 | 推理失败 | 否 | **平台/模型**（按澄清**不参与评分**，故不在优化范围） | — |

> 读法：**截断只出现在第 4 行的最后一列**，而且它是**你做的决定**——你返回多少条、按什么顺序，都是你的策略。**它不该被当成外部约束来抱怨，而该被当成一个可调旋钮。**

## 4. 三条推论

**推论 1**：大多数"记忆失效"案例，根因不在窗口大小。把它们归因于"上下文不够长"会**系统性误诊**，从而去优化错的东西（例如盲目换更大窗口的模型）。

**推论 2**：截断是可设计的。既然是你决定交出去什么，那么"交多少、交哪些、什么顺序"就是一个**策略空间**——而不是宿命。

**推论 3**：窗口越大，问题越像检索问题。这解释了为什么即使 1M 上下文可用，RAG/记忆架构依然存在且必要——**容量问题解决了，注意力分配问题没有**。

## 5. 是的，必须按场景设计——但先分清"哪一层该场景化"

用户的判断方向正确，但需要分层，否则会做出"每个场景重写一套引擎"的过度设计。

| 层 | 是否场景化 | 理由 |
|---|---|---|
| 机制/流水线（写入→存储→检索→组装） | **否，同构** | 任何场景都要做同样五件事 |
| 数据模型（Schema） | **是** | 事实、关系、时间、规则、敏感字段的形态差异极大 |
| 冲突/时效/遗忘策略 | **是** | "什么算过期"在不同场景答案完全不同 |
| 排序与预算策略 | **是** | 有的场景要"少而准"，有的要"全而广" |
| 拒答阈值 | **是** | 高风险场景必须敢于说"没有证据" |
| 服务契约（Add/Search） | **否** | 接口是外部给定的 |

### 5.1 场景的「记忆代价矩阵」（设计依据）

设计的本质是**把代价矩阵固化成策略**。五类错误 × 不同场景原型的代价：

| 错误类型 | 高风险专业问答<br>（医疗/法律/金融） | 长周期个人助理 | 长任务执行 Agent<br>（代码/运维） | 高并发客服 | 知识型分析 |
|---|---|---|---|---|---|
| 漏召回（该给的没给） | 中 | 中 | 高 | 中 | **极高** |
| 错召回（给了误导性证据） | **极高** | 中 | 高 | 中 | 低 |
| 时效错误（旧事实当新事实） | **极高** | **高** | **极高** | 高 | 中 |
| 冲突共存（自相矛盾） | **极高** | 中 | 高 | 中 | 低 |
| 越界泄露（跨主体/敏感） | **极高** | 高 | 中 | **极高** | 低 |

**由矩阵导出的策略优先级**（示例）：

- **高风险专业问答** → 精度优先 + 强制证据溯源 + 高拒答阈值；宁可空手也不能给错
- **长周期个人助理** → 时效正确 + 偏好漂移跟踪 + 冲突以"最近+来源"消解
- **长任务执行 Agent** → 当前状态精确（状态机式单值槽位）+ 版本/环境绑定 + 历史经验复用
- **高并发客服** → 召回稳定 + 低延迟 + 强隔离；精度适中
- **知识型分析** → 覆盖度优先 + 多跳组装 + 允许更多候选

> 观察：**同一套流水线，因为代价矩阵不同，策略参数几乎处处相反**（例如"预算该收紧还是放宽"在两个场景里结论相反）。这就是"必须按场景设计"的真正含义。

## 6. 两种产品策略

| 策略 | 形态 | 优势 | 代价 |
|---|---|---|---|
| **A. 横向：记忆基础设施** | 通用引擎 + 可配置参数 | 规模效应、一次开发多场景复用 | 高度同质化（市场上已有多个 3 万–6 万★ 的开源实现）；难以回答"你为什么更好" |
| **B. 纵向：场景记忆产品** | 单一场景深度定制 | 差异化清晰、可用场景指标证明效果 | 可迁移性差、单场景天花板低、获客面窄 |
| **C. 折中（推荐）：通用引擎 + 场景包** | 引擎不变，Scene Pack 以插件形式提供：Schema / 冲突规则 / 时效策略 / 预算策略 / 拒答阈值 | 兼得复用性与差异化；新增场景是加配置而非改架构 | 需要前期把"策略接口"抽象对，否则场景包会退化成 if-else 屎山 |

**判断**：A 的路已被走满（见 `03-projects.md` 的 Mem0/Graphiti/Cognee 等）；B 太窄。**C 是唯一同时具备复用性和差异化的位置**，且落地成本可控——前提是**先定义清楚"策略接口"**（哪些东西可插拔、在流水线哪一段生效）。

## 7. 回到赛事（AML）的启示

这一点很关键，因为它和产品策略**存在张力**：

- ✅ 平台在 **32 个数据源**上统一评测 → **过度场景化会掉分**。押注单一场景的纵深设计，在大规模异构评测上可能是负收益。
- ✅ 官方没有用"场景"来切分，而是用**能力项 A/B/C/D/E/G/H**（显式事实召回 / 关系与多跳 / 时间与事件序列 / 记忆治理 / 个性化与关怀 / 规则与流程 / 认识论安全与隐私）。→ **能力项本质上就是"场景无关的能力切面"**，官方用它们替代了场景划分。

**推论**：参赛策略应是

> **能力项对齐（保底）+ 策略可插拔（差异化）**

而不是"选一个场景做深"。也就是说：**第 6 节的 C 形态（通用引擎 + 场景包）恰好同时适配赛事与产品**——赛事只启用通用能力包，产品按场景挂不同场景包。

⚠️ 仍是未知项：**各能力项在 6000+ 实例中的占比没有公开**（见 `07-open-questions.md`）。这直接决定"该往哪个能力项押注多少"，是本方案最大的不确定性。

## 9. 一句话回答

> **是不是 token 截断导致 LLM 失忆？**
> 不是——截断只是表层。失忆是**五段流水线的复合损耗**：写入丢、存储乱、检索漏、组装脏、阅读弱。其中**只有"组装的超预算"算截断，而且那是你的选择**。窗口越大，问题越从"容量"变成"检索与注意力分配"。
>
> **是不是该按业务场景做针对性设计？**
> 是，但要分清层次：**机制同构，策略异构**。正确的产品形态是**通用引擎 + 场景包**——把场景的"记忆代价矩阵"固化成可插拔的策略（Schema/冲突/时效/预算/拒答阈值），而不是为每个场景重写引擎。
