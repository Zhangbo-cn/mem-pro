# 01 · 三赛道核心差异与推荐

> 官方名：Agent Memory Challenge 2026（AMC），统一平台 Agent Memory Leaderboard（AML）。用户已选**组别 = 开源方法榜**，本文档解决**赛道选择**。
>
> 📌 **最终决策（2026-10-14，用户拍板）：赛道 = 多模态记忆（Multimodal）。**
> 本文档的量化推荐为「文本 4.00 > 多模态 3.70 > 代码 2.95」；用户基于「多模态应用场景更多、可做内容空间更大、价值通用性更强」选择多模态。**决策已采纳**，本文保留推荐推导过程作为决策依据。
> 多模态的连带影响（合规风险、两层输出顺序、能力项体系重映射）见 `11-ordering-semantics-and-generality.md`。

## 一、任务形态与评测单元

| 赛道 | 输入（Add 写什么） | 检索（Search 问什么） | 样本组织 |
|---|---|---|---|
| 文本 | 多轮会话消息流；`messages` 数组按原顺序，每条含 role + 非空 content | 按**基准原文**检索（`query`），选择题额外在顶层传 `options`（不含金标） | 以 `user_id` 为隔离边界、`session_id` 标识来源会话；**同 user 跨 session 仍需跨会话检索** |
| 代码 | 仓库/会话轨迹（保留历史工程经验） | 面向同仓库历史工程经验的检索、筛选与复用 | 150 个软件工程任务 × relevant/noisy 两种记忆条件 = 300 次评测尝试 |
| 多模态 | 有序内容数组：字符串 **或** `text` / `image_url`（Base64 图片） | 查询可用同一 `text`/`image_url` 有序数组 | 按公开数据源单元与媒体限制处理 |

关键原文佐证 ✅：

- 文本分段规则：`普通文本在达到 20 条消息或 2,000 个词中的任一边界时确定性分段，词数按冻结 Adapter 计数；Streaming 按增量会话／任务单元写入；代码保留仓库／会话轨迹，多模态按公开数据源单元与媒体限制处理。单次请求最长 30 分钟。`
- 代码赛道目标（赛事公告口径，⚠️部分核实 - 来自用户转发的公告，官网 `/competition` 未见同句）：`最终以实际代码修改和测试验证结果为准，而非仅看检索相似度`
- 多模态原文：`平台发送原图及 caption；支持图片的系统处理原图，文本系统可忽略 image_url 并使用 caption。`

**差异要点**：文本是「会话流 → 记忆 → 答题检索」；代码是「仓库经验 → 检索 → 实际改代码并过测试」——**评测单元从"检索相似度"升级为"代码修改+测试验证结果"**；多模态是「图文混排内容数组 → 跨模态证据检索」。

## 三、指标与评分合同

平台固定（✅官方原文）：`你只负责 Add / Search 环节。回答模型、提示词、评分器、数据集组合、Top K 和汇总规则由我们统一固定`。

| 赛道 | 评分形态 | 官方给出的基准/指标线索 |
|---|---|---|
| 文本 | 平台统一 Answer + Eval，按题型固定评分规则，汇总各数据集与 Overall | 能力模型 RECALL / ADAPT / ACT（见下） |
| 代码 | `CAMBench Coding`（当前正式计分）；relevant vs noisy 相对比较 | **实际代码修改与测试验证**，非检索相似度（⚠️公告口径） |
| 多模态 | ATM-Bench（按**问题质量**等指标）、Mem-Gallery（**F1**，图集式记忆检索） | ✅`多模态 ATM-Bench 以问题质量等指标评估多模态智能体记忆能力。` / `多模态 Mem-Gallery 使用 F1 指标评估图集式记忆检索能力。` |

文本赛道能力模型 ✅（官方原文分类，逐字照录）：

- `01 RECALL 召回证据` — `A 显式事实召回`（事实、属性、来源与实体信息）、`B 关系与多跳组合`（跨片段证据与关系链恢复）、`C 时间与事件序列`（日期、间隔、顺序与轨迹变化）
- `02 ADAPT 形成稳定记忆` — `D 记忆治理`（更新、冲突消解、删除与遗忘）、`E 个性化与关怀`（偏好、背景、健康与心理关怀）
- `03 ACT 安全执行` — `G 规则与流程执行`（领域推理、程序执行与格式约束）、`H 认识论安全与隐私`（稳健拒答、最小披露与证据边界）

> ❓ **观察（存疑）**：官方页面列出的子能力标签依次为 A、B、C、D、E、G、H，**未出现 F 与 I**。是页面漏列还是编号有跳号，官方未说明。已列入 `07-open-questions.md`。

代码赛道任务分类 ✅：`A 99 题 缺陷修复`（`代码定位、根因分析、修复实现与回归验证`）、`B 51 题 功能增强`（`需求理解、接口设计、功能实现与测试适配`）、`C 4 档 噪声干扰等级`（`低、中低、中高与高干扰，覆盖全部 150 题`）；参考目录 `SWEContextBench`。

多模态能力分类 ✅：`A 7 个子能力 记忆认知`（检索、视觉推理与关系推理）、`B 4 个子能力 记忆演化`（时间推理、知识更新与持续学习）、`C 3 个子能力 记忆对齐`（个性化、拒答与证据治理）；官方注：`官网以三组能力呈现，底层仍保留 6 个能力类别与 14 个实际子能力。`（7+4+3 = 14 ✅ 自洽）

## 四、接口与资源约束

三赛道**共用同一套 Add/Search 契约** ✅：

| 契约项 | 官方原文 |
|---|---|
| 写入方式 | `同步` — `记忆写入完成后，Add 接口返回 HTTP 200` |
| 写后可见 | `每个记忆分块都必须在返回 HTTP 200 前完成持久化，并且能够立即检索。` |
| Top K | `正式外部评测固定为 100`；`返回数量不得超过 top_k ，超量会判为契约错误` |
| 检索范围 | `Add 和 Search 必须使用完全相同的 user_id`；`session_id ... 不作为 Search 的筛选条件` |
| 鉴权 | `Add / Search 支持 Token 、 Bearer 和 X-Api-Key ； none 仅用于公开 smoke。` |
| 未使用字段 | `现行规范不发送 metadata 、 app_id 、 agent_id 或 async_mode` |
| 单次请求上限 | `单次请求最长 30 分钟` |
| 响应形态 | Search 顶层为 `data` 数组；无结果返回 `{"data": []}`；`不要增加 items 包装层` |
| 地址要求 | `不得包含用户名、密码等凭据，也不得指向私有、回环或链路本地地址`；建议 HTTPS |

**赛道差异**：

- 多模态额外要求：`多模态写入 按有序内容数组接收文本和 Base64 图片`；`平台保留图片内容并进入统一 Answer 链路`（即必须能返回图片证据）。文本系统可忽略 `image_url` 只用 caption（官方原文，意味着纯文本方案在多模态赛道**可以跑但会丢分**）。
- 代码赛道：无额外接口字段差异，但记忆内容体积巨大（≈1.8B tokens），对写入吞吐与存储压力最大。

## 五、参赛门槛与工作量

依据：✅ Full 每 AML Key 每赛道最多 **2 次**、第 2 次须首次 Full 完成后 **30 天**；smoke `每小时 1 次；本届每赛道最多 30 次`。

| 赛道 | 自部署复杂度 | 需自建的数据管线 | 试错成本（2 次 Full 且间隔 30 天） |
|---|---|---|---|
| 文本 | **低**。单表/向量库即可起步 | 分段（20 条消息或 2000 词）、会话与 user 隔离、跨会话检索 | **低**。公开基准（LoCoMo/LongMemEval 类）可在本地自测，先把 smoke 打通再花 Full |
| 代码 | **高**。需仓库级检索 + 代码结构理解；响应要支撑"改代码+过测试"的检索质量 | 仓库解析、模块关系、版本辨析、噪声过滤 | **高**。本地难以复现"改代码+测试验证"的端到端链路，Full 前自测信号弱 |
| 多模态 | **中高**。需图片存储 + Base64 传输 + 多模态编码/OCR | 图文有序数组解析、图片对象存储、跨模态检索与图片证据返回 | **中**。ATM-Bench/Mem-Gallery 的本地替代基准少，自测信号一般 |

**共同硬约束**：`第二期不接受只提交 GitHub 仓库、Docker 镜像或启动说明并由 AML 代为部署`（✅开源与商业都适用）；`正式 Full 评测受理后，不得因结果不理想更换版本或撤回`（✅版本冻结）。

## 九、与本机现有资产的关系

**结论：本机没有与本赛事相关的既有代码资产可复用，需要从零搭建。**

| 项 | 实测状态 |
|---|---|
| 是否存在可复用的记忆系统代码 | **否**。本机没有与本赛事相关的实现，Add/Search 服务需自行新建 |
| 可用的通用开发环境 | Python 3 与 Node 环境可用；`curl` 可用（用于自测与官方接口联调） |
| 不安装重型依赖（任务纪律） | 选型必须偏向单机可跑、纯 Python 的轻量方案（见 `03-projects.md` 选型建议） |
| 网络限制（实测） | `github.com` 网页与 `huggingface.co` 直连超时；`api.github.com`、`raw.githubusercontent.com`、`arxiv.org`、`export.arxiv.org` 可达（见 `urlcheck.txt`） |

> 影响：与"拿现成项目改改"的团队相比，本方案需要**自建服务层**。因此选型应优先复用成熟**库**（如 txtai 的同步 add/search、pgvector 作存储），只自研差异化的检索编排层，避免重复造轮子。

## 十、结论与决策矩阵

### 打分矩阵

维度与权重（**已剔除"与本机既有资产契合度"维度** —— 本机无相关资产，该维度对三个赛道无区分度）：

| 维度 | 权重 | 权重依据 |
|---|---|---|
| 参赛门槛与工作量（越易越高分） | **0.30** | ⚠️ 官方 Full 第 2 次须首次完成后 30 天、而评测 11-04 停止 → **本届实际只有 1 次 Full**（见 `07-open-questions.md` §5）。没有试错机会，"能否稳妥交付"权重上调 |
| 竞争态势 / 拿奖难度（越易拿奖越高分） | 0.25 | 直接决定得奖概率 |
| 复用价值（技术可迁移性） | 0.20 | 成果的外部可用性 |
| 风险可控性（越低风险越高分） | 0.25 | 只有 1 次 Full，风险不可迭代，权重较高 |

| 赛道 | 工作量 0.30 | 拿奖 0.25 | 复用 0.20 | 风险 0.25 | **加权总分** |
|---|---|---|---|---|---|
| **文本** | 5 | 2 | 5 | 4 | **4.00** |
| **多模态** | 3 | 5 | 4 | 3 | **3.70** |
| **代码** | 2 | 4 | 3 | 3 | **2.95** |

计算：文本 = 0.30×5 + 0.25×2 + 0.20×5 + 0.25×4 = 1.50+0.50+1.00+1.00 = **4.00**
多模态 = 0.30×3 + 0.25×5 + 0.20×4 + 0.25×3 = 0.90+1.25+0.80+0.75 = **3.70**
代码 = 0.30×2 + 0.25×4 + 0.20×3 + 0.25×3 = 0.60+1.00+0.60+0.75 = **2.95**

> **⚠️ 敏感性说明（诚实披露）**：本矩阵对权重敏感。若把"工作量"权重降回 0.25、"拿奖"提到 0.30（即认为可承受交付失败风险、只搏名次），则文本 ≈ 3.85、多模态 ≈ 3.80，**差距缩到 0.05 以内、近乎并列**。
> 因此本推荐的实质是：**在"本届只有 1 次 Full"的前提下，把可交付性放在第一位 → 选文本**；若用户判断可以承受交付失败风险、以名次为唯一目标，则多模态同样成立。

### 推荐（单选）

> ## ✅ 推荐赛道：**文本记忆（Textual）**

理由：

1. **时间可行**：距今 ~17 天（材料截止 2026-10-31 23:59），且本届只有 1 次 Full。文本赛道可直接复用成熟开源库 + 单机轻量存储，是唯一能稳妥走完"自部署 + Smoke + 第一次 Full"的赛道。
2. **复用价值最高**：会话记忆与检索编排属通用能力，成果可平移到客服、助理、知识库等多类场景；代码赛道的能力迁移面窄得多。
3. **成本最低**：≈300M tokens（代码 ≈1.8B，是多模态的 2.25 倍、文本的 6 倍）。
4. **自测信号最强**：LoCoMo / LongMemEval 类公开基准可在本机预演，降低"2 次 Full、间隔 30 天"的试错风险。
5. **风险最可控**：多模态的模型约束（FAQ 05）若成立，对多模态是致命的；文本受影响最小。

主要代价：**竞争最激烈**（拿奖难度最高，该维度仅得 2 分）。但"进不了奖"与"交不出有效提交"相比，后者更致命——先确保有效提交，再谈名次。

### 备选

> **多模态记忆（Multimodal）** —— 若用户的目标是**博取名次**而非稳妥完赛，且团队具备图片链路基建，则多模态更优：第二期新增赛道、参赛者最少、复用价值中高。
> **代码记忆（Coding）** —— 仅当团队有强 SWE/仓库检索背景且能承受 ≈1.8B tokens 成本时考虑。**不推荐**，因为与现有资产契合度最低且工程量最大。

### 决策触发条件（供用户拍板）

- 若决定 **稳妥完赛 + 成果可迁移** → 选**文本**（默认推荐）。
- 若决定 **搏名次且已有图片链路** → 选**多模态**。
- 若 **FAQ 05 的模型约束确认适用于开源方法榜** → 强烈倾向**文本**（多模态编码受限将导致方案空间极窄）。
- 若用户能投入 ≥2 名全职工程师且 ≥4 周 → 才考虑代码赛道。

| 项 | 结果 |
|---|---|
| 组别 | 开源方法榜（早前已定） |
| **赛道** | **多模态记忆（Multimodal）** |
